# SwiftVM 机制演进设计

日期：2026-09-14。起点：`e6f3e9f`。目标是可靠地运行 x86-64 程序，并改善实际热点的编译与执行成本。FEX 用于发现问题和交叉验证；实现方式服从 SwiftVM 的函数 IR、固定客体寄存器、代码对象、直接链接和 QSBR 架构。

## 已确认的设计边界

- 保留函数内跨块分析和多入口代码对象。无需为了模仿另一分配器而退回逐块分配。
- 保留原有规范区域优先的合并顺序。根数量减少不能代替主机指令数、正确输出和实际时间的改善。
- 优化只改变可证明安全的范围。RBP、RSP、FS、GS 本身都不能证明地址只属于当前线程。
- 编译质量与编译工作量分别设预算。代码块数量上限无法限制反复分配、反复合并和重复编译的开销。
- 32 位执行和图形库转发是产品能力扩展，不是修复 x86-64 JIT 的前置条件；不在本轮引入兼容性框架。

## 八项缺口的处理方式

| 范围 | 采用的方案 | 完成条件与依赖 |
| --- | --- | --- |
| 区域组织 | 基于热点出口选择相邻代码对象；稳定保留旧区域，按收益和成本决定是否重新组织 | 正确性、指令量和短负载结果均通过；依赖可撤销的编译结果与版本校验 |
| 寄存器压力 | 保留函数线性扫描；整段溢出按整段使用成本选择，局部重载窗口再考虑下一次使用 | scratch 验证始终成立；区间拆分和 FPR 重载需要单独扩展位置描述 |
| 编译并发 | 编译准备、独立生成、串行发布分离；同一客体入口合并重复请求 | SMC 与配置变化能拒绝过时结果，发布前不改动活动代码对象 |
| 内存排序 | 每个解码器持有不可变模式；无逃逸证明不放松地址排序；能力验证后才能采用硬件模式 | 先启用现有软件排序降低默认风险；完整 TSO、屏障消除和自动硬件模式需分别验证 |
| 信号 | 将客体事件、客体状态恢复和信号帧构造分层；按 Linux ABI 支持备用栈、真实故障信息和返回 | 依赖可靠的客体读写权限与精确故障位置；不能把所有异常统一作为宿主进程退出 |
| 虚拟内存 | 统一客体映射记录，保存权限、文件与偏移；由宿主页能力决定直接映射或软件检查 | 4 KiB 权限在 16 KiB 宿主页内仍真实生效；共享映射保持可见性和文件生命周期 |
| Linux ABI | 以实际程序启动与退出路径排序：目录和管道、健壮锁退出、信号，再评估进程创建 | 每个系统调用有完整错误与生命周期语义；进程创建需先拆分共享状态 |
| 32 位与库转发 | 保留独立扩展边界，按具体应用需求立项 | 32 位地址空间、结构布局和系统调用不可只改 ELF 检查；库转发需专门 ABI 与资源所有权 |

## 首批实现：内存排序状态和分配工作量

### 排序模式归属

`X64Decoder` 构造时接收 `TsoMode`。函数区域和独立块两个入口都从各自地址空间配置传入模式。移除进程全局排序变量，解码期间不再读取另一实例能够改变的值。

`AcqRel` 的标量、SSE 和 VEX 访问不再通过栈或段寄存器名字绕过排序。SSE、SSE4 的直接访存以及 Push/Pop 也统一进入排序接口。保留已有的显式 `Relaxed`、`Hardware` 行为及 LOCK 处理。磁盘缓存版本递增，排除旧的栈/TLS 放松代码。

定向运行还发现并修复了 LRCPC 地址计算的寄存器破坏：直接地址模式下 x10 可保存活跃 SSA 值，不能作为固定地址临时寄存器使用。带偏移的 LDAPR/STLR 现在使用分配器检查过的临时寄存器；带地址偏移的内存窗口模式继续使用其保留寄存器。原有字节表循环在直接地址及两种窗口大小下均验证通过。

LRCPC 对齐检查也不能改写 NZCV：新增的“比较、访存、SETZ”短用例在修复前将不相等错误地报告为相等。加载和存储的检查改用不影响条件码的位测试分支，同时覆盖对齐与非对齐地址。

实际短渲染暴露了另一个跨阶段问题：分配器认可的低 32 位视图在发码复核时因遗漏 `StoreMemoryTSO` 而触发断言。两个阶段现在共用 `low32_copy.h` 中的消费约束；普通和有序存储均保留源寄存器。新增发码用例在修复前稳定触发该断言，修复后通过。

窗口模式的小数转换还暴露了使用时点不一致：后端把窄位提取的源读取推迟到下一条算术指令，但重载区间只覆盖到原来的提取位置。该值可能仅存在于重载寄存器中，栈槽并未写入。现在溢出源保留显式提取，遵守分配器已验证的使用时点。新增 U8/U16 发码检查在修复前均检测到未写入栈槽的读取；最小 `strtod("1.0")` 客体也在修复前返回错误结果、修复后通过。后续若要恢复这类融合，应在分配前改写 IR，或显式扩展并验证位置契约。

这不代表整个运行时已实现实例隔离或全部 x86 内存模型已经通过验证。助手地址归属由下面的第二批实现继续处理。启动器及 `X86Instance` 的默认模式和非法值回退改为 `acqrel`；直接构造 `Config`、`X64Decoder` 时仍保留原有默认值，需要调用方明确选择。默认值变更减少了未配置启动时的弱排序风险，完整 TSO 仍需独立验证。

后续排序设计采用两层：正确性配置决定允许的行为，优化只删除已被证明冗余的屏障。硬件模式需要宿主能力与当前执行线程均成立，不能把“某种 CPU 支持”当成所有线程已经开启。显式弱排序仅用于已知工作负载的性能实验。当前硬件模式仍是调用方的承诺，自动能力验证尚未实现。

### 整段溢出的选择

SwiftVM 目前通过重新分配让一个 SSA 值的整个区间落栈。若只按压力点之后的下一次使用选择，可能把已经频繁读取的早期部分一起落栈。因此先比较整个区间的不同使用位置数，再比较下一次使用位置；仍相同则按区间结束位置和定义编号稳定选择。

使用记录只在出现寄存器压力时收集，处理位转换别名、可达块、终结分支和循环保留值；没有溢出的代码不增加一次使用扫描。使用次数是静态成本近似，不是假定的运行次数。固定寄存器、保留寄存器和无法满足目标区间约束的寄存器仍不得驱逐。

找到需要重试的候选后立即结束本次分配，不继续生成即将丢弃的结果。每个单元最多进行 8 次可选驱逐重试，超过后丢弃这些尝试，进入 scratch 保留量验证路径。普通路径失败后，允许末级尝试把全部动态 GPR 留给临时值和重载。窗口模式同样需要这个出口，不能只给最高固定寄存器等级开放。所有等级最终仍未通过验证时均显式失败，移除原来记录警告后继续发码的行为。上限约束编译工作量，不能代替最终分配验证。

不在本轮把 SSA 值的位置从单一寄存器改成跨边的多段位置。真正的局部拆分需要后端在每个使用点查询位置，并给控制流边提供显式复制；直接扩大当前重载窗口会在合流、助手调用或故障恢复时产生错误。

## 第二批实现：取指和助手地址归属

原来的全局 `MemoryImpl` 会在创建新实例时被覆盖，旧实例随后编译的代码来自新实例的窗口。REP 和 x87 助手还从另一组进程全局变量读取偏移与掩码，因此已经缓存的机器码也会访问错误窗口。

取指接口现由 `X86Instance::Impl` 持有，偏移与掩码构造后不可变，其生命周期覆盖地址空间及其 IR。函数区域、独立块以及 ENDBR 边界检查均使用该接口。`Runtime::Run` 根据自己的配置建立 `GuestMemoryScope`，JIT 和解释器中的助手读取当前宿主线程的作用域；嵌套执行或异常退出会恢复前一个作用域。未进入 Runtime 的独立助手继续使用直接地址。无需改变助手参数 ABI 或客体寄存器布局。

回归检查先复现了错误取指（预期 `0x11`、实际 `0x22`），以及关闭扩展固定寄存器时旧实例的 REP 写错窗口。默认固定寄存器配置还暴露了 `CallLambda` 预算过大：发码仅租用一个 NZCV 合并临时寄存器，却被按三个收费，并另外计入参数和结果的重载。现按实际发码路径声明一个临时寄存器，保留固定调用目标及重载的独立计费和最终验证。分配诊断开关下可以查看具体失败指令的可用量与需求。

修复前证据：[取指串实例](/private/tmp/swiftvm-instance-fetch-before-20260914.log)、[助手串实例](/private/tmp/swiftvm-instance-helper-before-pin0-20260914.log)、[默认分配拒绝](/private/tmp/swiftvm-instance-ra-20260914.log)。

新增短测试覆盖：两个实例交替编译和运行、缓存助手跨实例复用、不同窗口掩码、高位客体地址、第二个实例销毁后的继续执行，以及助手前后的条件码。作用域检查还覆盖嵌套、异常恢复和两线程同时持有不同映射，只有一次同步及少量字节写入。

本批只消除取指与助手的地址配置共享。`SignalHandler` 的映射检查回调仍是进程级接口，Linux 启动器、AOT 和 guest-call 都使用它；下一步需统一迁移到地址空间，并保留宿主信号回调的安全访问方式。当前不宣称完整多实例隔离，也未开启并行编译。

## 下一阶段：代码生成与发布分离

当前 `Translate` 的大锁覆盖了解码、区域选择、IR 操作、代码生成及发布。直接减小锁范围会让旧代码退休、块所有权转移和新入口发布发生竞争。

采用三步事务边界：

1. 在短临界区取得配置、入口所属对象、映射版本和所需客体字节。对正在处理的同一入口登记唯一任务，其余请求等待该结果或继续已有代码。
2. 任务私有的 IR、分配结果、机器码和重定位信息独立生成。此阶段不转移活动块、不修补直接链接、不从入口表移除旧对象。
3. 在发布临界区复核映射、代码字节及对象版本。过时结果直接丢弃或按有限次数重试。有效结果统一安装入口并更新链接；旧对象继续经现有失效与 QSBR 流程回收。

需要先为上述版本定义语义：写入代码页、取消映射、改变可执行权限、重组所有权都会使相关生成输入失效。不能只在编译开始查一次缓存，也不能仅凭页号相同接受结果。客体在翻译期间改写代码的检测，还需与当前 SMC 模式保持一致。

先用单线程实现这条生成与发布通路，再允许不同入口同时生成。取指与助手的地址偏移和掩码现已独立；并发开启之前还必须迁移进程级映射检查回调，并审核分配器、模块和代码缓存的共享写入。这样可以分别验证生命周期正确性和并行收益。

## 区域重组的收益规则

先记录实际运行中的跨对象出口命中次数，仅对持续命中的边考虑重组。候选集合保持现有 64/128 块限制，并另设客体字节量、IR 大小及累计重编译预算。暂不增大默认区域。

收益来自消除常见出口的状态写回、分派和边界复制；成本包括代码复制、寄存器压力、编译时间及指令缓存增长。首次候选可以只在受控配置下生成对照结果，不自动替换活动对象。只有结果成立才经统一发布流程替换。

`has_code` 边界不会直接删除。已发布目标通过显式所有者关系参与候选选择；未知间接目标、不同配置、版本变化或预算耗尽均保留外部出口。一次合并失败应进入冷却期，避免循环合并与拆分。

## 兼容性层的具体边界

映射管理先建立单一客体事实来源：地址区间、读写执行权限、匿名/文件来源、共享属性、文件偏移和持有的文件对象。宿主 `mprotect` 是实现手段，不能替代客体权限。宿主页覆盖多个客体页时，若权限不一致，必须使用细粒度软件检查或具备等价保护能力的后端；返回成功但不执行权限不是可接受的兼容模式。

信号队列保存来源、信号号、代码、故障地址和相关客体 PC。异步信号在安全点递送；同步故障先利用现有客体状态映射恢复准确状态，再构造帧。备用栈要处理范围、对齐、嵌套以及返回后状态恢复；系统调用重启与进程停止语义单独实现，不能靠同一个待处理位概括。

健壮锁退出需要在客体内存上做有界链表遍历，验证指针和长度，并按所有者死亡语义更新 futex 与唤醒等待者。线程退出、进程退出和异常退出必须汇合到同一清理入口。进程创建需要先定义地址空间、文件表、信号动作和线程对象的复制/共享规则；不以调用一次宿主 `fork` 代替这些契约。
